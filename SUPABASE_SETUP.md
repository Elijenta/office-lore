# Office Lore — Supabase setup

Status: **done and verified.** This file is now a reference for what was set up, in case you need to reproduce it (new environment, new Supabase project, onboarding someone else to the setup) — not a to-do list.

## What's live

- Project URL: `https://pldhdsopdwmgvuvwdsta.supabase.co` (hardcoded in `index.html`, along with the publishable/anon key — safe to expose in client code, Row Level Security is the real protection layer).
- Schema: [`supabase/0001_schema.sql`](supabase/0001_schema.sql) — tables, RLS policies, XP-ledger triggers, Realtime.
- [`supabase/0003_xp_cleanup_triggers.sql`](supabase/0003_xp_cleanup_triggers.sql) — required companion migration so deleting a nickname/quote/anecdote/counter/beer (or moving a Perfect Pour vote) correctly reverses the XP it granted, instead of leaving it stale.
- [`supabase/0002_seed_demo_data.sql`](supabase/0002_seed_demo_data.sql) — optional example content, not run on the live project.
- [`supabase/0004_abt_dynasty.sql`](supabase/0004_abt_dynasty.sql) — **The Abt Dynasty**: `abt_reigns` table (persisted reign history) + a trigger on `xp_events` that automatically crowns/dethrones based on live Beer XP standings. Nothing in the app ever writes to this table directly — only that trigger does.
- [`supabase/0005_beer_session_editing.sql`](supabase/0005_beer_session_editing.sql) — required for **Edit Session**: broadens Beer Club RLS so any of the 3 users can edit an existing session's date/location/participants/beers/ratings/consumption (not just the original creator/row-owner — a session is a shared group log), and adds a delta-XP trigger so editing a quantity only awards/revokes XP for the difference. This also fixed a latent bug where the original "create session" flow could silently fail to save other participants' scores, since the old owner-only insert policy rejected any row that wasn't the creator's own.
- [`supabase/0006_standalone_beer_ratings.sql`](supabase/0006_standalone_beer_ratings.sql) — required for **"Rate this beer"** on the beer detail page: makes `session_id` nullable on `beer_ratings`/`beer_consumption` and adds `rated_at`/`context` columns, so a personal rating can exist with no Beer Session at all. Reuses every existing XP trigger unchanged (none of them reference `session_id`).
- [`supabase/0007_beer_consumption_updated_at.sql`](supabase/0007_beer_consumption_updated_at.sql) — adds `updated_at` to `beer_consumption` (kept current via a trigger reusing `set_updated_at()`). Trivial, additive.
- [`supabase/0008_safe_deletes.sql`](supabase/0008_safe_deletes.sql) — required for **safe delete functionality**: broadens `beer_sessions`/`perfect_pours`/`counter_events` DELETE RLS to any authenticated user (same "shared group log" reasoning as `0005`, and required so a full session delete's cascade doesn't hit a foreign-key violation on rows owned by someone else), and replaces the `beer_consumption` XP-cleanup trigger with a smarter version: deleting the row that earned "new beer tried" XP now reassigns that XP to another remaining consumption row of the same beer/user if one exists (instead of just losing it), and revokes "own beer adopted" XP if a delete drops a beer's distinct-drinker count back under 2. Frontend gained: remove-one-beer-line and remove-participant (both immediate + confirmed, scoped to exact session+user+beer), quantity-to-0 routes into the same removal confirmation, a "Delete Session" danger action (single cascading delete), a usage check before deleting a beer from the Beer Database, and delete on individual counter +1/-1 history entries. All hard deletes, no audit trail — consistent with every other delete already in the app.
- [`supabase/0009_poetry_wall.sql`](supabase/0009_poetry_wall.sql) — **Poetry Wall**: new `poems`/`poem_reactions` tables plus `poet_laureate_reigns` (a direct mirror of `abt_reigns`/`check_abt_throne` from `0004`, same partial-unique-index-for-one-active-reign + advisory-lock pattern, own lock key so it never serializes against Beer XP writes). Publishing a poem grants +5 Poetry XP (`xp_type='poetry'`, a new allowed value added to `xp_events.xp_type` and to the `user_xp_totals` view); each reaction received grants +1; both non-author users giving 🔥 Actually Good grants a one-time +5 bonus, tracked via `poems.actually_good_bonus_awarded` and correctly revoked/re-awardable if a reaction is toggled off/back on. A trigger enforces max 3 distinct reactions per user per poem; RLS blocks reacting to your own poem. Poem delete cascades cleanly (reactions + all their XP + the publish/bonus XP, zero orphans) — verified directly against `xp_events` including the reassignment-adjacent "toggle a reaction off mid-way" edge cases. Editing a poem never re-grants publish XP (the trigger is `after insert` only).
- [`supabase/0010_nickname_reactions.sql`](supabase/0010_nickname_reactions.sql) — **Nicknames: Legendary + Doubt reactions**: widens `nickname_votes.vote_type` to allow `'legendary'`/`'doubt'` alongside the existing `'funny'/'accurate'/'savage'`. No RLS/XP changes needed (votes never granted XP, policies were already generic). Frontend gained: a "🔥 LEGENDARY NICKNAME" badge that appears once all registered users have voted Legendary on a nickname and disappears the instant one retracts (purely derived, nothing stored), a new Cards/Compact view switcher on the Nicknames page (choice persisted in `localStorage`, survives reload and realtime refresh), a first-ever detail modal (nothing like it existed before — Compact rows click through to it), and 8 sort options shared between both views. Savage's display icon changed from 🔥 to 💀 (🔥 now means Legendary) — display-only, the underlying `vote_type` string is unchanged.
- [`supabase/0011_nickname_battles.sql`](supabase/0011_nickname_battles.sql) — **Nickname Battles (Phase 1, no Championship yet)**: new `nickname_battles`/`nickname_battle_votes` tables plus a `nickname_battle_vote_counts` view. Both nicknames' text/real-name/business-unit are denormalized onto the battle row at creation time (in addition to the FK) so battle history stays stable even if a nickname is later edited or deleted. Votes are hidden from other users until a battle resolves — enforced by RLS (`using (user_id = auth.uid() or battle.status <> 'open')`), not just the UI — while the vote *count* stays visible throughout via the view (`total_votes` is always live, `votes_a`/`votes_b` only become real once resolved). Auto-finalizes the instant all 3 users have voted via a trigger (`resolve_nickname_battle_outcome`, per-battle `hashtext()`-derived advisory lock so concurrent votes can never double-finalize or race — a deliberate deviation from the single-global-lock pattern `0004`/`0009` use, since a global lock here would serialize unrelated battles against each other for no reason), or manually via `close_nickname_battle_early()` (RPC, landing on a draw if tied — the only realistic draw path with 3 voters and 2 options). No XP — ordinary battle wins are prestige-only per spec; only a future Championship win would grant a small bonus. Frontend gained a "⚔️ Battles" tab inside Nicknames (Hall of Champions, Recent Battle Activity, active/history battle lists), a dramatic reveal overlay reusing the existing Abt Dynasty confetti/overlay mechanism, Rematch on a draw, and a Battle Record stat block on the nickname detail modal. Championship/bracket tournament is intentionally deferred to a follow-up migration.
- [`supabase/0012_poetry_challenges.sql`](supabase/0012_poetry_challenges.sql) — **Poetry Challenges**: a new `poetry_prompts` table (seeded with ~41 prompts across 7 categories, plus 6 curated "Give Me Something Stupid" entries) and 4 new columns on `poems` (`prompt_id`, denormalized `prompt_text_snapshot`/`prompt_category_snapshot`, `is_challenge_poem`) — same "freeze a snapshot alongside the FK" pattern as `nickname_battles`, so a challenge poem's displayed prompt stays correct even if the source prompt is later edited/deactivated (verified directly: deactivating a prompt mid-test left an already-published poem's detail page unaffected). The +3 challenge bonus lives inside the *existing* `xp_on_poem_insert()` trigger from `0009` rather than a new one, so the same INSERT-only guarantee that stops the base +5 from being re-granted on edit covers the challenge bonus too, with zero extra bookkeeping — verified a challenge poem grants exactly +8 (5+3) once, editing grants nothing further, and deleting reverses both. The Daily Challenge is deterministic and unstored (a date-string hash picks an index into the eligible prompts), so every client computes the identical prompt for the same calendar day with no cron job or "today's pick" table — verified identical across two separate calls. Frontend gained the prompt-picker card atop Poetry Wall (Accept Challenge / Give Me Another / Give Me Something Stupid, with session-only recency exclusion so prompts don't repeat back-to-back), the Daily Challenge section with a "SAME PROMPT. DIFFERENT POETS." comparison once ≥2 users complete it, a Challenge Board leaderboard, and Challenge stats on the profile page.
- [`supabase/0013_nickname_edit_permissions.sql`](supabase/0013_nickname_edit_permissions.sql) — **Bugfix: nickname edit rights**. The `nicknames` UPDATE RLS policy has always been creator-only, but the frontend issued one plain full-field update for every editor — a non-creator's edit silently matched zero rows (Supabase doesn't error on an RLS-filtered update with no matching rows), so their changes always appeared to save but never did. Fixed with two flows: the creator keeps using the existing full `.update()` through the unchanged owner-only RLS policy; anyone else now goes through a new `update_nickname_collaborative_fields(p_nickname_id, p_description, p_anecdote)` RPC whose SQL statement is structurally incapable of touching any column besides `description`/`anecdote` — safe against a manipulated API call, not just a disabled frontend field (verified: a raw non-owner `.update()` on protected fields still affects 0 rows, an unauthenticated RPC call is rejected, and passing an unexpected extra parameter fails outright since the function signature doesn't accept it). Added `updated_by_user_id`, set automatically by a `before update` trigger regardless of which path performed the write, so "Added by" (`created_by_user_id`, never changes) and "Last edited by" can be shown separately. No XP changes needed — `trg_xp_nickname_insert` was already `after insert` only, so editing (by anyone, any number of times) has never been able to re-grant the +10 creation XP.
- [`supabase/0014_daily_poetry_challenges.sql`](supabase/0014_daily_poetry_challenges.sql) — **Daily Poetry Challenge overhaul**: new `daily_poetry_challenges` table, one row per calendar date, written exactly once by `get_or_create_daily_challenge()` (same read-only-for-clients pattern as `abt_reigns`/`poet_laureate_reigns` — nothing else ever writes here). Unlike the old client-derived Daily Challenge (a bare object/scenario prompt, recomputed independently by every client), this is genuine shared server-side state: the subject is always either an existing nickname or one of the 3 real users (a race-safe 50/50 pick via a per-date advisory lock, deterministic per calendar day), combined with one of 9 categories (2 new: `deep_thoughts`/`wholesome`) and a matching absurd `%s`-template prompt — identical for all clients on the same day, never regenerated on refresh/realtime/re-login. `poems` gained `daily_challenge_id`/`is_daily_challenge`, plus a partial unique index enforcing max 1 official daily-challenge poem per user per day (`View/Edit My Entry` replaces the write button once submitted; deleting resets status back to "Not attempted"). No new XP trigger — a daily-challenge poem is submitted with `is_challenge_poem = true`, so the *existing* `xp_on_poem_insert()` trigger from `0009`/`0012` already grants the normal +5/+3 with zero extra bookkeeping, and it's `after insert` only so editing never re-grants it. Frontend gained a `✒️ Write Today's Poem` action (missing before), a distinct `📜 DAILY CHALLENGE` badge (vs. the plain `🎯 Challenge Poem` badge for regular prompts), and a richer detail-page info block. **Follow-up bugfix in the same file** (found live during verification): the "user" subject pool must be scoped to the 3 oldest `profiles` rows (`order by created_at asc limit 3`) — an earlier version queried unscoped `profiles`, which had accumulated 10 leftover QA/test accounts from prior testing rounds alongside the 3 real users (Elien/Nick/Atti), so it could occasionally pick a test account as the challenge subject.
- **Per-participant beer consumption bugfix** (no new migration — pure frontend rewrite): the session form used to default every beer×participant cell to "drank 1, rated 7" the moment a beer was toggled on, so adding a beer for one person could silently save it for everyone in the session. Fixed by replacing the matrix with explicit per-participant "+ Add beer for {Name}" actions — a beer entry now only ever gets created for the participant it was explicitly added for. No existing data was touched or auto-corrected; if a past session has a beer wrongly attributed to someone, open Edit Session and remove that one line for that one person.
- [`supabase/0015_app_memberships.sql`](supabase/0015_app_memberships.sql) — **Bugfix: strict per-app user isolation**. This Supabase project is shared with an unrelated second app (QuestNest), which means one `auth.users` table. `handle_new_user()` used to fire on *every* signup project-wide, so anyone who signed up through QuestNest's own signup form got an Office Lore `profiles` row and, since RLS was a blanket `using (true)` on nearly every table, full read access to all Office Lore data — confirmed live as the cause of QuestNest test accounts polluting Office Lore's leaderboards and dropdowns. Fixed with a new `app_memberships` table (`app_id`, `user_id`, `role`, `is_active`, unique on `app_id+user_id`) as the single source of truth for "is this auth user actually part of Office Lore," backfilled with the 3 real users. Every table's RLS gained an `is_app_member('officelore')` gate (via a `security definer` helper function, needed to avoid RLS self-recursion when checking `app_memberships` from inside its own policy); `profiles` additionally got a row-level filter so even a member only ever sees *other members'* profile rows, not every row in the table. `handle_new_user()` now only creates a profile when the signup explicitly passed `{ app: 'officelore' }` in its metadata — closing the leak at the source rather than just hiding it downstream. `check_abt_throne()`/`check_poet_laureate_throne()` needed no direct changes since they only ever query the `user_xp_totals` view, which now joins through `app_memberships`; `get_or_create_daily_challenge()`'s ad hoc "3 oldest profiles" heuristic (a workaround from the `0014` round for this exact problem) was replaced with a real membership join. Two `security definer` RPCs (`update_nickname_collaborative_fields`, `close_nickname_battle_early`) bypass table RLS entirely by design, so they needed their own explicit membership guard; same for the `nickname_battle_vote_counts` view, which is owner-run and queried directly by the client. No users were deleted — non-member profile rows (leftover test/QA accounts) simply stop being returned to Office Lore members anywhere, verified live: `profiles` went from 5 visible rows to exactly 3 (the real users) for a member, with the 2 stray rows still existing in the table but no longer visible through RLS. Membership is admin-only — there's no client insert/update/delete policy on `app_memberships`, so granting or revoking access is a manual `insert`/`update ... set is_active` in the SQL editor (see below).
- Auth: **self-service sign-up stays open** (no allowlist on who can create an `auth.users` account — Authentication → Providers → Email → "Confirm email" is **off**, so signup logs a session in immediately), but as of `0015`, creating an account no longer grants access to Office Lore's data. Access is gated separately by `app_memberships` — see "How people get in" below.

## Reproducing this from scratch (new project)

1. Create a Supabase project ([supabase.com](https://supabase.com) → New project).
2. SQL Editor → run `0001_schema.sql`, then `0003_xp_cleanup_triggers.sql`, then `0004_abt_dynasty.sql`, then `0005_beer_session_editing.sql`, then `0006_standalone_beer_ratings.sql`, then `0007_beer_consumption_updated_at.sql`, then `0008_safe_deletes.sql`, then `0009_poetry_wall.sql`, then `0010_nickname_reactions.sql`, then `0011_nickname_battles.sql`, then `0012_poetry_challenges.sql`, then `0013_nickname_edit_permissions.sql`, then `0014_daily_poetry_challenges.sql`, then `0015_app_memberships.sql`. `0002_seed_demo_data.sql` is optional (edit the 3 placeholder emails near the top first if you use it). If reproducing on a project that will *only* ever run Office Lore (never shared with another app), `0015` is still safe to run — it just means every signup happens to be the only "app" around — but its `app_memberships` gate is what makes the "how people get in" step below actually take effect.
3. Authentication → Providers → Email → turn "Confirm email" off (unless you want people to click a confirmation link before first login).
4. Project Settings → API → copy the Project URL and the publishable/anon key, paste them into the `SUPABASE_URL` / `SUPABASE_ANON_KEY` constants near the top of `index.html`'s `<script>`.
5. Open `index.html`, click "Registreren" on the login screen to create the first account, then grant it access per "How people get in" below — a fresh signup lands on "Nog geen toegang" until you do.

## How people get in

Anyone with the app's URL can click **Registreren** and create an `auth.users` account — that part is still open, no allowlist. But since `0015_app_memberships.sql`, creating an account no longer grants access to any Office Lore data: `handle_new_user()` only creates a `profiles` row (nothing more), and every table's RLS requires an active `app_memberships` row with `app_id = 'officelore'`. A fresh signup sees "Nog geen toegang" (no access yet) and can't get past it on their own.

**To grant access** to a new colleague, find their `auth.users` id (Authentication → Users in the dashboard, or `select id from auth.users where email = '...'`) and run in the SQL editor:
```sql
insert into public.app_memberships (app_id, user_id) values ('officelore', '<their-user-id>');
```
**To revoke access** without deleting their account or data:
```sql
update public.app_memberships set is_active = false where user_id = '<their-user-id>' and app_id = 'officelore';
```
"Wachtwoord vergeten?" on the login screen handles password resets via Supabase's email flow (needs "Confirm email"-style mail delivery to work, so make sure your Supabase project's SMTP/email sending is functional if you rely on this) — unrelated to membership, works the same regardless of `app_memberships` status.
